# Руководство для AI coding agents

Этот файл должен быть конкретным, актуальным и пригодным для реальной работы. 

---

## Назначение

Этот файл является основным операционным руководством для AI-агентов, работающих в репозитории.

Он должен давать агенту достаточно контекста, чтобы:

- понимать, что делает проект;
- следовать правильной архитектуре и принятым соглашениям;
- класть код в правильные директории;
- запускать нужные команды для setup, проверки и тестирования;
- избегать небезопасных и некачественных изменений;
- понимать, когда нужно остановиться и спросить человека.

## Принципы Работы Агента

Если пользователь явно не попросил иначе, агент должен:

- предпочитать минимальное безопасное изменение, которое решает задачу;
- сохранять существующую архитектуру (Vanilla JS) и naming conventions;
- обновлять тесты (при их появлении) при изменении поведения;
- обновлять docs, config и examples, если они устаревают из-за изменений;
- проверять результат перед завершением работы;
- не делать спекулятивных рефакторингов;
- спрашивать перед разрушительными, необратимыми, дорогими или влияющими на production действиями (например, очистка LocalStorage пользователя).

### На Что Агент Должен Оптимизировать Работу

1. Correctness (Соответствие ТЗ `technical_specifications.md`)
2. Maintainability (Чистота JS кода, разбиение на модули)
3. Speed (Оптимизация работы с DOM)

### Чего Агент Не Должен Делать По Умолчанию

- Переписывать архитектуру без запроса (например, не предлагать перенос на React/Vue).
- Добавлять новую зависимость (npm-пакеты, фреймворки), если задачу можно решить встроенными средствами браузера.
- Редактировать сгенерированные файлы вручную, если в проекте принят соответствующий workflow.
- Не игнорировать адаптивный дизайн при верстке.

## Архитектура

- Архитектурный стиль: modular monolith (Vanilla JS modules)
- Высокоуровневое описание: Приложение состоит из статических HTML-страниц. Каждая страница подключает необходимые JS-скрипты, отвечающие за свою изолированную логику. Общие утилиты и работа с хранилищем вынесены в отдельные файлы.
- Основные модули / bounded contexts: `form` (поиск запчастей и запись), `storage` (взаимодействие с LocalStorage), `utils` (вспомогательные механизмы).
- Основной поток данных: user input -> validation (JS) -> query internal structured object / LocalStorage -> render HTML updates -> safe to LocalStorage.
- Подход к управлению состоянием: Переменные JavaScript + браузерное хранилище (LocalStorage).
- Жёсткие ограничения: Никаких внешних баз данных, только клиентские технологии. Код должен быть разделен на файлы (main.js, form.js и пр.).

### Архитектурные Правила

- Логику работы с DOM для каждой страницы размещать в профильном файле (например, список/поиск в `form.js`).
- Функции по извлечению и сохранению данных размещать в `storage.js`.
- Все JS-функции должны быть именованными, а не анонимными (за исключением стрелочных функций в колбеках, например `addEventListener`).

### Ответственность Директорий

| Путь | Ответственность | Типичное содержимое | Чего быть не должно |
| --- | --- | --- | --- |
| `/styles/` | Хранение внешнего вида проекта | `style.css`, `index.css` | JS скрипты, HTML страницы |
| `/scripts/` | Бизнес-логика, работа с DOM, хранение | `form.js`, `storage.js` | CSS стили, большие фрагменты HTML |
| `/assets/` | Медиаресурсы | `.jpg`, `.png`, `.svg` | Код |

### Правила Размещения Файлов

- Новые скрипты логики размещать в `scripts/`.
- Общие CSS файлы размещать в `styles/`.
- Изображения размещать в `assets/`.
- Все создаваемые HTML страницы класть в корень проекта `/`.

3. manual test: запуск локально, проверка функционала в браузере.

## Стиль Кода И Naming

- Formatter: Prettier / IDE formatter
- Политика типизации: dynamic (чистый JS)
- Политика комментариев: Ясные и точные комментарии к ключевым блокам, а также разбиение блоков (как в `form.js`).
- Политика импортов: Подключение модулей внизу HTML тела (`<body><script src="..."></script></body>`)
- Подход к обработке ошибок: JS Alert / DOM alerts (по ТЗ: "При ошибке - alert с сообщением"), fallback-значения.
- Подход к конфигурации: Конфиг/Начальные данные хранятся в объектах JS (как `serviceData` в `form.js`).

### Naming Conventions, Которые Мы Предпочитаем

| Сущность | Предпочтительно | Избегать | Пример |
| --- | --- | --- | --- |
| Файлы JS/HTML | kebab-case / lowercase | mixedCase | `service.html`, `form.js` |
| CSS Классы | kebab-case (BEM-style optional) | snake_case, CamelCase | `form-group`, `btn-primary` |
| JS Переменные | camelCase | snake_case | `brandInputEl`, `modelDropdownEl` |
| JS Константы | UPPER_SNAKE_CASE / camelCase | - | `MAX_MILEAGE`, `serviceData` |
| Функции | verbNoun (camelCase) | generic names | `getLevenshteinDistance`, `renderAutocomplete` |

### Style Do / Don't

Делать:

- использовать понятные названия переменных на английском;
- использовать именованные функции вместо анонимных;
- сохранять читаемость, комментировать сложные участки.

Не делать:

- превращать один `main.js` в свалку (разделять на `form.js`, `storage.js` и т.д.);
- оставлять `console.log` в финальной версии;
- вводить слишком сложные абстракции, выходящие за рамки требований учебного проекта.

## Границы Безопасности И Safety

### Жёсткие Правила

- Никогда не коммитить API ключи к сторонним сервисам (если такие появятся).
- В проекте нет бэкенда. Любые данные обрабатываются клиентом.
- Не импортировать уязвимые внешние cdn-скрипты.

### Перед Этими Действиями Нужна Подтверждённая Проверка Человеком

- Удаление или радикальная смена структуры HTML (может сломать привязанные JS-скрипты).
- Изменение структуры сохраняемых данных в LocalStorage (существующие сессии пользователя могут сломаться).

## Git, PR И Definition Of Done

- Схема именования веток: `main` (или понятные `feature/*` названия).
- Формат commit message: Отражающий суть (Например: `feat: добавлен функционал поиска марки`, `fix: исправлен баг с LocalStorage`).

### Definition Of Done

Изменение не считается завершённым, пока:

1. Не запущен и не проверен HTML файл.
2. консоль разработчика (`F12`) не пуста от JS-ошибок (`Uncaught TypeError` и т.д.).
3. Данные корректно записываются и читаются из LocalStorage (если затрагивается логика данных).
4. Размещение файлов и naming соответствуют этому документу.

## Известные Подводные Камни

- Смена структуры `index.html` или классов элементов сломает работу `form.js` (`document.getElementById`). Агент должен проверять наличие элементов на всех подходящих страницах перед внесением изменений в поиск DOM-узлов.
- Валидация форм должна происходить чисто через JavaScript перед отправкой, а не с помощью нативного HTML `required` (требование ТЗ), хотя `required` может присутствовать для семантики.
